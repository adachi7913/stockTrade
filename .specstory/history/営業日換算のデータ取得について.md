## 営業日換算のデータ取得について (2025/2/14 10:32:58)

_**User**_

fetch_range = (int(os.environ.get("FETCH_DATA_RANGE", ""))*365)+73
２年分のデータを取ろうとして、変数に2 * 365 + 73となっていますが
営業日換算だと365はもっと減りますね？
何日でしょうか

---

_**Assistant**_

一般的には、1年あたり約252営業日となります。  
つまり、2年分のデータであれば、約252 × 2 = **504営業日**となります。

理由としては、カレンダー上の365日から週末（土日）や祝日などの非営業日分を除くと、約252日程度になるためです。

---

_**User**_

添付ファイルにおいて、想定通りの日数分のデータを
yFinanceから取得する処理になっていますか？

---

_**Assistant**_

添付されているファイルでは、環境変数 `"FETCH_DATA_RANGE"` で指定された年数に対して、1年あたり約252営業日と換算し、その後に追加で73日分を加えています。たとえば、もし `"FETCH_DATA_RANGE"` に `2` が設定されている場合、

\[
(2 \times 252) + 73 = 577 \text{ 日分}
\]

のデータ取得を試みる形になっています。

**補足説明:**

- **252営業日について**  
  通常、1年あたりの市場の営業日は約252日と考えられており、365日ではなく252日分のデータを基準にするのが一般的です。

- **73日の加算について**  
  追加の73日分は、インジケーターの計算など、過去のデータが必要な場合のバッファとして利用されている可能性があります。これにより直近の営業日分以外にも、計算に必要な過去のデータを確保できます。

**結論として、**  
ファイル内の処理は、営業日に換算した想定通りの期間（＝252営業日ベース）に加えて追加日数を取得するようになっているので、意図通りの日数分のデータをyFinanceから取得する処理になっています。ただし、yFinanceから返されるデータは市場カレンダーに基づいているため、厳密な日数が常に一致するとは限らない点は留意してください。

_**Assistant**_

下記のように、`dao.fetch_no_entry_info(stock_code)` の返却値がタプル以外（例えば int 型）の場合にも対応するよう修正してください。  
具体的には、値がタプルの場合は通常通りアンパックし、整数の場合は直近のエントリー日付を `None` として、整数の値を `no_entry_span` に設定するようにします。

以下、修正部分のコード例です。

```python:service/ai_rule_service.py
def process_stock(stock_code):
    load_dotenv(override=True)
    if os.getenv("STOP_GEMINI_FLAG", "false").lower() == "y":
        return

    dao = StockDAO()
    try:
        company_info = dao.fetch_company_info(stock_code)
        if not company_info:
            logging.error(f"企業情報取得失敗: {stock_code}")
            return

        industry_name = TableCategory.get_table_prefix(company_info[3])
        full_data = dao.get_stock_full_data_period(stock_code, industry_name)
        if not full_data:
            logging.error(f"株価データ取得失敗: {stock_code}")
            return

        # --- フィルター処理 ---
        latest_record = full_data[-1]
        close_price = float(latest_record.get("close", 0))

        # DAOから時価総額および最新のエントリー不可情報を取得
        market_cap = dao.fetch_market_cap(stock_code)
        no_entry_info = dao.fetch_no_entry_info(stock_code)
        # 修正: no_entry_info の返却値がタプルでない場合の対応を追加
        if no_entry_info is not None:
            if isinstance(no_entry_info, tuple):
                last_entry_date, no_entry_span = no_entry_info
            elif isinstance(no_entry_info, int):
                last_entry_date, no_entry_span = None, no_entry_info
            else:
                logging.error(f"{stock_code}: 予期しない形式の no_entry_info: {no_entry_info}")
                last_entry_date, no_entry_span = None, None
        else:
            last_entry_date, no_entry_span = None, None

        from lib.stock_filter import filter_stock
        # full_data 内の各日付の出来高（float型に変換）
        volume_data = [float(record.get("volume", 0)) for record in full_data]
        # 最新の指標データの取得
        atr = float(latest_record.get("atr", 0))
        rsi_val = float(latest_record.get("rsi", 0))
        stoch_k = float(latest_record.get("stoch", {}).get("stoch_k", 0))
        if not filter_stock(stock_code, close_price, market_cap, last_entry_date, no_entry_span, volume_data, atr, rsi_val, stoch_k):
            return

        # --- Gemini API 呼び出し ---
        handler = ApiHandler(full_data)
        response = handler.call_gemini_api()
        time.sleep(5)
        if (isinstance(response, str) and response.startswith("Gemini API call failed")) or (isinstance(response, dict) and response.get("error")):
            logging.warning(f"{stock_code}: Gemini APIエラー発生のためスキップ")
            return

        logging.info("銘柄コード: %s", stock_code)
        logging.info("Gemini API response: %s", response)
        insert_data = parse_response(full_data, response)
        if not insert_data:
            logging.error(f"生成された挿入データが無効: {stock_code}")
            return

        dao.insert_api_response(insert_data)
    except Exception as e:
        error_msg = traceback.format_exc()
        logging.error(f"銘柄 {stock_code} 処理中エラー: {e}")
        create_error_message(error_msg)
    finally:
        try:
            dao.close()
        except Exception:
            pass
```

この修正により、`no_entry_info` が整数で返された場合にも `last_entry_date` と `no_entry_span` が適切に設定され、エラーが回避されます。

予想取得件数より、実際に取得した件数と大きく乖離がある原因はなんですか？

---

_**Assistant**_

上記ログから考えられる原因はいくつかあります。

1. **市場実際の営業日数に基づく返却**  
   yFinance API は、指定した期間内のすべてのカレンダー日ではなく、実際に取引が行われた営業日のみのデータを返します。  
   たとえば、環境変数 `"FETCH_DATA_RANGE"` で 2 年分（理論上 504 営業日＋追加分）のデータを指定しても、実際にはその企業が取引されている取引日（営業日）が少ない場合があります。

2. **企業の上場日や取引開始日**  
   もし対象の銘柄 77520 の上場日や取引開始日が、指定した期間よりも後の場合、その銘柄は指定期間の全営業日のデータが存在しません。  
   結果として、理論上の「予想最大件数」よりも実際の取得件数が少なくなります。

3. **休日や市場休場日**  
   さらに、国や市場の休日、または休場日なども影響し、指定された日数分すべての営業日のデータが揃うとは限らないため、実際のデータ件数に乖離が生じる原因となります。

以上の点から、ログに記録された「取得件数: 387件, 予想最大件数: 556件」という差異は、  
指定した期間に対する理論上の営業日数と、実際にその銘柄が取引されている営業日数との違い（および上場日などの制約）に起因すると考えられます。

_**User**_

では実取得件数は、土日祝などを鑑みると妥当な数値と判断できますかね？

---

_**Assistant**_

以下のように考えるのが妥当です。

- **取引が実際に行われた営業日分のみ返却**  
  yFinanceは、カレンダー上のすべての日付ではなく、実際に株式が取引された営業日のデータのみを返します。したがって、土日や祝日で市場が休みの場合はデータ件数が減るのが当然です。

- **上場日やデータの開始日も影響**  
  銘柄によっては上場日が指定期間内ではない場合や、流動性の低い銘柄などで取引日数が理論上の最大値に達しないケースもあります。

ログの場合、予想最大件数が556件となっていますが、実際に387件取得されていることから、  
「市場が休みの日（週末・祝日）がある」や「該当銘柄の取引状況（初登場日が指定期間の途中からなど）」が影響していると考えられ、妥当な結果であると判断できます。

つまり、**はい、土日祝などの休場日やその他の取引上の制約を考慮すると、実取得件数387件は現実的な値と言えるでしょう。**

_**Assistant**_

以下のログや各モジュールの実装内容から、全体のデータフローにおいて以下のような点で不備や懸念事項があると考えられます。

---

### 1. yfinance からの株価データ取得と前処理

- **欠損値の補完（fillna(0) の影響）**  
  yfinance で取得したデータに対して `df.fillna(0, inplace=True)` としているため、本来は欠損している（データが存在しない）箇所を 0 で埋めています。  
  → その結果、各テクニカル指標（例：ATR、移動平均、ボリンジャーバンド）の計算時に「初期値」として 0 が多数含まれ、実際の市場状況を反映できなくなっています。ログ中にも「提供されたデータに初期値（0.0 または 'UNKNOWN'）が多く…」という指摘があるように、これがエントリー不可の原因となっています。

- **「open」の値の不整合**  
  ログの中で「open の値に誤りがある」と指摘されている箇所が複数報告されています。  
  → これは欠損値補完や、yfinance から取得したデータの前処理（例えば、正しい日付のソートや、欠落した日付の存在チェックなど）が原因の可能性があります。結果として、実際に計算される指標やシグナルが信用できない状態になっています。

---

### 2. インジケーター計算と API への入力

- **計算対象データの不備**  
  `IndicatorCalculator` クラス内では、各インジケーター（Ichimoku, ADX, BB, STOCH, ATR, RSI, MACD, dynamic_threshold, weekly_trend, PCAシグナル）を算出していますが、もし入力となる株価データに欠損（や 0 での埋め込み）が存在すると、算出結果も“0”や`UNKNOWN`になってしまいます。  
  → ログでも「各指標が初期値のまま」という内容が目立ち、十分なデータがない状態でバックテストやエントリールールの構築が行われないように判断されていることがわかります。

- **PCA や weekly_trend の計算**  
  ローリングウィンドウや日付の変換で、十分な期間のデータがない場合（もしくは前処理がうまく行われていない場合）、これらの計算結果が `NaN` や 0 となってしまい、Gemini API に渡すデータが不十分になる可能性があります。

---

### 3. Gemini API のレスポンスパース処理

- **Markdown コードブロック形式への依存**  
  `Gemini/api_handler.py` 内の `_extract_json` メソッドでは、レスポンスが ```json ... ``` に囲まれている場合のみ中身を抽出しています。  
  → もし Gemini API のレスポンスが必ずこの形式になっていなかった場合、パースに失敗して例外が発生する可能性があります。パースに失敗した際は、レスポンスの生テキストをそのまま理由として保存しているため、DB へ挿入される内容が予期しないものになりかねません。

---

### 4. DB 挿入周り（DAO層）の不備

- **日付のフォーマット変換依存**  
  `dao/stock_dao.py` の `insert_indicator_data` では、日付が 8 文字（YYYYMMDD）の場合にハイフンを含む形式（YYYY-MM-DD）に変換しています。  
  → もし、取得した日付が既に期待外の形式や、不正な値であった場合、DB 挿入に失敗する可能性があります。

- **銘柄コードの前処理**  
  複数の箇所で、銘柄コードの末尾に "0" がある場合に取り除く処理が実装されています（例：`stock_code = stock_code[:-1] if stock_code.endswith("0") else stock_code`）。  
  → この処理が一律に正しく適用されない場合、DB の companies テーブルとの結合や参照時に不整合が発生する恐れがあります。

- **エラーハンドリングの不十分さ**  
  DB 挿入時、あるいはコミット時に例外が発生した場合、ロールバックなどの処理は行っているものの、挿入データそのものに問題があった場合のログ出力や通知機能が不足しているように見受けられます。

---

### まとめ

全体として、以下の点が懸念されます。

- **データ取得段階での前処理の過程**  
  → yfinance からのデータが欠損時に 0 で埋められることで、本来の株価や指標算出に必要な値が正しく反映されず、後続のインジケーター計算に影響を及ぼしている。

- **インジケーター算出時のデータ不足**  
  → 欠損値や初期値のままのデータが多いため、Gemini API が「エントリー不可」と判断する結果になっている。

- **API レスポンスの変換・パースの脆弱性**  
  → レスポンス形式が期待通りでない場合のエラー処理が十分ではなく、結果として挿入されるデータの内容が正しく処理できていない可能性がある。

- **DB 挿入前のフォーマット変換と銘柄コードの整合**  
  → 日付や銘柄コードの変換ルールが一部依存的であり、想定外のデータ（例：形式が異なる日付や、末尾の "0" の扱い）により、DB にデータが正しく挿入されないことも起こり得る。

これらの点から、株価評価フローのデータ挿入処理において、前処理の段階・計算ロジック・レスポンスのパース、そして DB 挿入時のフォーマット変換の各工程で、いずれも不備が起こる可能性が指摘されます。特に「初期値（0 や UNKNOWN）が多い」とログ上で示されている点は、各段階でのデータ検証や補正の見直しが必要であると考えられます。

- **フィードバックループの活用**  
  実際のトレード結果やバックテスト結果をもとに、ルールのパラメータや閾値を定期的に評価・調整する仕組みを取り入れると、システム自体が環境に適応しやすくなります。ユーザーのフィードバックも加味し、過去の実績に基づく調整が有効です。

- **ボーダーラインでの検証**  
  もし閾値の調整によって「ギリギリ」の銘柄が多数出ている場合、その銘柄に対してはより詳細なリアルタイムデータや第2のシグナルを追加で検討するなど、補助的な判断基準を設ける方法も考えられます。

これらのアイディアを組み合わせることで、極端に絞り込みすぎず、かつリスクを適切に管理できるバランスの良いエントリールールの構築が期待できます。試行錯誤しながら、現状のルールと市場環境に合わせた最適なパラメータを見出すことが重要です。
